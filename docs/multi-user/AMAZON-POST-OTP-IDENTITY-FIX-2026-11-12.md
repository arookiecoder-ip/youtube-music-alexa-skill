# Amazon identity confirmation after OTP

After the MFA redirect fix, the reported account reached AlexaPy's successful login state after OTP. The following additional identity check called `AlexaAPI.get_authentication()`, which targets only the configured marketplace. AlexaPy's session confirmation can succeed through its amazon.com fallback while the configured marketplace still rejects the session. The extra call returned `AlexapyLoginError('Unauthorized')`, resulting in the user-visible “Amazon could not confirm this account's identity” error.

The server now captures the canonical customer email and ID from the exact authenticated `/api/users/me` response that AlexaPy uses to confirm the session. This preserves the successful marketplace fallback. It publishes that snapshot only after successful confirmation and only when its customer ID matches the ID established by AlexaPy. There is no second request to the failing endpoint, no fallback to a typed email, and no weakening of the linked-account check.

The capture is restricted to HTTP 200 responses from known HTTPS Amazon customer endpoints on the configured marketplace or amazon.com, at the default HTTPS port, with no URL credentials. Both www and Alexa hostnames are recognized for compatibility with the session-confirmation endpoints in installed AlexaPy versions. Missing/incomplete profiles, failed confirmation, invalidated/closed sessions and customer-ID changes cannot authorize identity publication. The snapshot resets before each new confirmation and on reset.

The failed-promotion path also now closes the pending login and removes its staging directory. Successful promotion removes staging leftovers while keeping the adopted login and its promoted cookie open. The session adapter forwards AlexaPy's connector assignment to the real aiohttp session during close, so connector ownership stays consistent. Existing working account sessions and cookies remain isolated and preserved on failed replacement.

Validation includes the real AlexaPy OTP flow with a mocked Amazon transport, followed by identity publication, actual staged-cookie persistence and cleanup. That test passes against the deployed AlexaPy 1.34.0 dependency. The runtime-specific group also covers email/mobile identifiers, marketplace fallback, untrusted/malformed profiles, closed or invalidated sessions, redirects and persisted-session restoration: 18 cases passed. No real Amazon credentials or OTPs were used in automation.

A fresh real-account sign-in remains the final provider check: choose **Start over**, submit the Amazon credentials and OTP, then confirm the account shows connected and the intended Echo devices appear. Existing token, account eligibility, access-toggle and linked-Amazon authorization rules continue to apply. No Android compilation is required for this backend change.

The complete isolated backend/web-logic regression runner passed all 121 files (91 Python files and 30 JavaScript files), with zero failures/errors/skips in the Python reports. The final OTP-to-promotion integration case was also rerun independently and in the deployed dependency runtime. Deployment checks confirm readiness HTTP 200, invalid Alexa-token HTTP 403, source hashes matching the reviewed implementation and account rows preserved against the private pre-deployment backup.
