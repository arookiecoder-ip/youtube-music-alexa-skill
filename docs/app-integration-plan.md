# Implementation Plan — App + Backend, Two Repos, Nothing Breaks

Repos:
- Backend: `https://github.com/arookiecoder-ip/youtube-music-alexa-skill.git` — branch `master` = prod (Echo live). Freeze it.
- App: `https://github.com/arookiecoder-ip/JUKES.git` (fork of `https://github.com/rajeet-04/JUKES.git`) — branch `beta` = stable base (mirrors upstream `beta`, v2.3.5-beta). All app work on a feature branch OFF `beta`. `main` is not used.

## Phase 0 — Ground rules

1. No direct commits to `master` (backend) or `beta` (app fork). Everything via PR after testing.
2. No local Android builds — the laptop never runs `./gradlew` and needs no Android SDK/Gradle installed. Every APK (test + release) comes from GitHub Actions artifacts, downloaded and installed on the phone.
3. Backend prod container is never rebuilt until the feature branch is proven on staging.
4. NO hostname change, ever, in this plan: prod `alexa.synthora.in` keeps serving Echo exactly as before. Staging shares the SAME hostname under the `/staging/*` path prefix (no DNS edits, no new site block — one `handle_path` addition inside the existing site block; existing prod paths match first and are untouched). Port 443 is already open; the host firewall drops everything else, so no direct-port design.

## Phase 4 — Backend staging on the VPS (same hostname, one Caddy route)

Python has no compile; `docker compose build` is the build. Prod must not share a folder with test. The prod hostname and DNS are NEVER changed. Add only the `/staging/*` route to the existing Caddy site, validate, and reload Caddy once. Preserve all existing production routes and other site blocks.

1. On the VPS, keep two checkouts side by side:
   - PROD (existing): `/home/ubuntu/youtube-music-alexa-skill/` → `git checkout master` → `docker compose up -d` (today's stack: `ytmusic` + `youtube-browser` sharing the external `gluetun` netns + `caddy`, volumes `ytmusic_*`). Echo uses this. Rebuild here only at promotion.
   - STAGING (new): `/home/ubuntu/ytm-staging/` → `git clone https://github.com/arookiecoder-ip/youtube-music-alexa-skill.git`, `git checkout feat/backend-for-app` → staging stack.
2. Staging compose — STANDALONE file, not an overlay. `docker-compose.staging.yml` is a full copy of `docker-compose.yml` with these edits (do NOT use `-f docker-compose.yml -f <overlay>` merge tricks, and do NOT copy `network_mode: container:gluetun`):
   - WHY no `network_mode: container:gluetun`: prod already binds `:5000` (Flask, hardcoded `flask-server/Dockerfile:19`), `:5001` (Alexa login proxy, `alexa_remote.py:113`), `:6080` (noVNC, `browser-auth/Dockerfile:6`), `:8765` + `:5900` (browser control/VNC, hardcoded `browser-auth/entrypoint.sh:13-17`) inside the single gluetun netns. A second stack in the same netns bind-conflicts on all of them, and `network_mode` containers have no DNS name so nothing could route to them by name.
   - Instead staging runs on the shared `web` network with service-name routing (each container keeps default ports on its own IP — zero code changes needed): `container_name: ytmusic-staging` + service `youtube-browser-staging`, both on `networks: [web]`; volumes `staging_cache / staging_data / staging_alexa_cookies / staging_chromium_profile`; NO `caddy` service (reuse the existing production Caddy).
   - Direct phone access WITHOUT a new hostname and WITHOUT opening firewall ports: Caddy (already on 443, already on the `web` network) routes the SAME hostname by path — `handle_path /staging/* { reverse_proxy ytmusic-staging:5000 }` appended inside the existing site block. `handle_path` strips `/staging` before proxying, so Flask sees its normal routes; existing prod paths (`/youtube-login/*`, `/alexa/proxy/*`, `/`) keep matching first, Echo traffic is unaffected. The test APK talks to `https://alexa.synthora.in/staging` (proper TLS, no cleartext needed).
   - `.env.staging` (VPS-only, never committed — add it to `.gitignore` on the feature branch): own `API_KEY`, own `SECRET_KEY`, own `YT_BROWSER_CONTROL_TOKEN`, `PUBLIC_BASE_URL=https://alexa.synthora.in/staging` (MUST be this base or `get_stream` returns unplayable direct URLs) and `SITE_ADDRESS` unused by staging, plus `ALEXA_PROXY_BASE_URL=https://alexa.synthora.in/staging` (defaults to `PUBLIC_BASE_URL`, set explicitly to be safe) and `YT_BROWSER_SERVICE_URL=http://youtube-browser-staging:8765`.
   - Known trade-offs: staging egress is the datacenter IP, not the VPN (YouTube bot-checks may fail more often there). Acceptable for app-contract testing (JSON shapes, proxy streaming, queue semantics); VPN parity is restored at promotion when prod rebuilds. If exact VPN parity is ever required, the alternative is a SECOND gluetun container (`gluetun-staging` + own WireGuard credentials + `FIREWALL_INPUT_PORTS`), not sharing the existing one. (Staging traffic itself is full TLS through Caddy on 443 — same as prod.)
   - Gluetun firewall: NO change needed for this design. Both staging services live on the existing external `web` bridge; staging publishes no host ports.
3. Caddy: add and version the single `handle_path /staging/*` block before the production catch-all, inside the existing site block. Validate before one reload. No new hostname, DNS change, or site block. On this VPS the route is already active, so no reload is needed when applying the remaining fixes. Keep VPS-specific extra site blocks intact; do not replace the live Caddyfile with the repository template.
4. Deploy loop: laptop pushes `feat/backend-for-app` → SSH to VPS → `cd /home/ubuntu/ytm-staging && git pull && docker compose --env-file .env.staging -p staging -f docker-compose.staging.yml up -d --build` → `docker logs -f ytmusic-staging`. Prod containers keep running their old images; separate volumes mean a staging build cannot rewrite prod code or data.

Two stacks, two data sets: prod (`ytmusic`, `ytmusic_*` volumes, inside gluetun netns, via Caddy/`alexa.synthora.in`) vs staging (`ytmusic-staging`, `staging_*` volumes, on `web` bridge, via `https://alexa.synthora.in/staging` (same hostname, path prefix).
